# Requirements

This document records the behaviour implemented by the trade store.

## Trade record

Each current trade has:

| Field | Owner | Rule |
| --- | --- | --- |
| `trade_id` | Client | Required identifier, 1–64 characters, matching `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$` |
| `version` | Client | Required integer from 1 through 2,147,483,647 |
| `counterparty_id` | Client | Same identifier rules as `trade_id` |
| `portfolio_id` | Client | Same identifier rules as `trade_id` |
| `maturity_date` | Client | Date only. Must be on or after the current business date |
| `created_date` | Client on insert | Date only. The source system's original creation date. Preserved on every later replacement |
| `store_created_at` | Server | Timezone-aware UTC timestamp. Set once, when this service first stores the trade |
| `store_updated_at` | Server | Timezone-aware UTC timestamp. Set when the row is inserted, replaced, or newly marked expired |
| `expired` | Server | Boolean. Clients cannot send it |

Unknown JSON fields are rejected. A client-supplied `expired` or `updated_date` is a validation error, not a value the server stores.

## Version rules

There is one current row per `trade_id`.

1. Insert the trade when the ID does not exist. The response is `201`.
2. Replace the row when the incoming version is greater than the stored version. The response is `200`.
3. Replace the row when the incoming version equals the stored version. The response is `200`.
4. Reject a lower incoming version with `409` and leave the stored row unchanged.
5. Do not retain the previous row.

The check and the write share one database transaction. The transaction takes a PostgreSQL advisory lock on the trade ID before reading the row, then locks the row itself. Concurrent requests for the same ID are serialized. A slower older version cannot overwrite a newer version that has already committed.

A `BEFORE UPDATE` trigger is a second guard. It raises SQLSTATE `P0001` if a statement would store a lower version. The application maps that failure to `409`.

Equal versions are last-write-wins for the economic fields. `created_date` still stays at its original value.

## Dates, timestamps, and expiry

- `updated_date` is generated by the server in UTC. Naive timestamps are rejected by the persistence layer.
- The business date is the calendar date in `BUSINESS_TIMEZONE`. The default zone is `UTC`.
- A maturity date equal to the business date is valid for that whole business day.
- A maturity date before the business date is rejected with `422` and code `maturity_in_past`. The row is not written.
- The database does not enforce the maturity rule. The business date moves, so yesterday's valid trade must remain stored until the worker expires it.
- On an accepted insert or replacement the server stores `expired = false`. A replacement of an already expired trade becomes active again when the new maturity date is still valid.
- The expiry worker sets `expired = true` where `expired` is false and `maturity_date` is before the worker's current business date. It updates `updated_date` only for rows whose flag changes.
- Running the worker again is a no-op for rows that are already expired.
- The worker is a separate container and process. API workers do not start a scheduler.

## Bulk ingestion

`POST /trades/bulk` accepts `{"trades": [ ... ]}` and returns one result per input element, in the same order.

- A valid item is committed even when another item fails.
- Each item uses its own transaction.
- Validation, maturity, version, and unexpected database failures are isolated to that item.
- Database errors are logged by exception type. The response does not include SQL, connection strings, or stack traces.
- An empty list, a non-object body, extra envelope fields, or more than `BULK_MAX_ITEMS` trades rejects the whole request with `422`. Oversized batches are not partially processed.
- The overall status is `200` when every item is created or replaced, and `207 Multi-Status` when at least one item is rejected.

### Duplicate trade IDs inside one batch

Items are applied from first to last. Each later item sees earlier committed items in that batch.

Implications:

- The last accepted version for an ID wins.
- A later equal version replaces the row and still preserves the original `created_date`.
- A later lower version is `409`, including when an earlier item in the same batch created the trade.
- An earlier failed item does not roll back a later successful item.
- Callers that repeat an ID in one batch get sequential, not atomic, results. There is no batch-level rollback.

## Errors

Error responses use one envelope:

```json
{
  "error": {
    "code": "version_conflict",
    "message": "Incoming version is lower than the stored version.",
    "details": {}
  }
}
```

Health probes are the exception. `/health` and `/ready` return a `status` field so orchestrators can read them without parsing the domain envelope. `/ready` returns `503` with `{"status": "unavailable"}` when the database check fails, and the body does not include the driver error.

## Assumptions

- Identifiers are case-sensitive.
- `created_date` may be in the future or the past. It is a source-system date. `store_created_at` is the time this service first accepted the trade.
- The maturity check uses the process clock and the configured business timezone, not the database session timezone. Database sessions still set their timezone to UTC.
- A bulk request larger than the configured maximum is rejected in full so a caller cannot bypass the limit by mixing invalid items.
- No authentication is in scope for this prototype.
